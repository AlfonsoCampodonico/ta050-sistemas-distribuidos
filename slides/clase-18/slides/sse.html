El stream de vuelta

Un evento por token, y un proxy que puede arruinarlo

Content-Type: text/event-stream

data: {"delta":"La "}

data: {"delta":"luz "}

data: [DONE]

directo o con un proxy que reenvía

un token cada 40 ms

con un proxy que junta la respuesta

los 60 tokens juntos a los 2,5 s

En nginx: proxy_buffering off, o el header X-Accel-Buffering: no.

go run ./cmd/servidor · go run ./cmd/proxy -buffer · medido con curl

Tiempo: 1:13–1:18 (5 min, con demo). Idea clave: cada token sale apenas existe, como un evento en una respuesta HTTP que queda abierta; cualquier salto que junte la respuesta rompe el streaming. Decir: la respuesta es server-sent events: Content-Type text/event-stream, y cada evento es una línea data: seguida de una línea vacía. El formato exacto cambia según el proveedor. En el camino de vuelta, el gateway cuenta los tokens de salida y el navegador agrega cada fragmento. Demo en vivo. En una terminal: go run ./cmd/servidor -speed 2 (puerto 8080), go run ./cmd/proxy (8081, reenvía cada evento) y go run ./cmd/proxy -buffer -addr :8082 (junta la respuesta). En otra, el mismo curl -N contra los tres puertos, con el pedido del README. Directo o con el proxy que reenvía, cada evento llega unos 40 ms después del anterior y la respuesta de 60 tokens termina a los 2,4 s. Con el proxy que junta, no aparece nada durante 2,5 s y después llegan los 60 tokens de golpe: el servidor mandó cada token a tiempo, pero el cliente ve un solo bloque al final. El caso real es nginx con proxy_buffering activado, el valor por defecto. Se arregla desde el proxy, con proxy_buffering off, o desde el servidor, mandando el header X-Accel-Buffering: no; el servidor del repositorio lo manda.
